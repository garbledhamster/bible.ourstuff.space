# Chapter concept boards

Use **Concept Generation** between [Plan](project-phases.md#plan) and [Build](project-phases.md#build). Take the agreed outcome for each applicable chapter and show what it will look like before implementation. Keep the board and the decisions with the project.

## Use the same grid in every chapter

1. Put one wide lead image across the top. Show the outcome that explains why the chapter matters.
2. Put four smaller, captioned panels below it in two columns. Use them for related moments, screens, states, references, or details. Place them in the order the reader should look at them.
3. Make each image open at full size. Keep its caption short. On a narrow screen put the four panels in one column and keep their reading order. Start from the [working board template](concept-board-template.html).
4. Include a locator from the owning chapter, the source for each artifact, its review status, and the ticket that uses it. Reuse a visual across chapters when it shows the same thing.

Use mockups for interfaces and games, storyboards for sequences, and diagrams or document compositions for technical, operational and verification chapters. Label expected results as planned. If a chapter does not apply, record why in the chapter.

## Keep build tickets easy to open

Put the complete ticket ID beside the panel or choice it belongs to. In the Project Bible reader, highlight the full ID in a chapter or project document to read the ticket in place. Use the ticket buttons in Work queue and Build handoff when you’re starting from the task sheet. A project board that runs the shared ticket viewer can use the same selection behavior. [Choose how to read a chapter](project-phases.md#choose-how-to-read-a-chapter)

## Make approval usable in Build

Keep the approved image and its version. For software UI, record the reference viewport, exact font families and sizes, spacing, component dimensions and positions, colors, controls, and states. For game scenes, record the viewport, camera, scale, positioning, animation and interaction cues. Put the required values in a specification beside the image. Annotate anything that cannot be faithfully reproduced by inspecting the image alone.

Record the creator’s answer by board or panel. Identify the filename or revision they approved and the tickets that depend on it. If artwork or a layout varies by target, keep the primary view and the changed target view together. Treat edits to approved material as new design revisions.

Start Build with the approved board and specification. Compare the implemented result with the reference at the intended sizes and link both versions from the owning chapter. Keep measured results and observations distinct from the concept.
