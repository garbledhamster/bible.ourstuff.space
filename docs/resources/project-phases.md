# Project phases

Start every project in Grilling. Keep the current phase near the top of the project’s Bible, above the chapters. Write it on its own line, for example `**Current phase:** Build`. The reader shows the phase number and name under the project title. Update the line when the work moves to a new phase. For an existing project, use the phase that matches the work and evidence for its current release.

The phase tells you what kind of work you’re doing. The chapter tells you where the decision, task, or result belongs. Each applicable chapter has instructions for all five phases. A single-player project can mark Multiplayer N/A and carry on.

## Start to finish

1. Find or create your project folder and follow the [setup instructions](../AGENTS.md) to initialize the repository, install the shared Bible, and set up the project Bible and task list.
2. Set the current release and phase at the top of the project Bible. Start at [Vision & Scope](game-bible-guide.md#vision--scope), and work through the chapters that apply in order.
3. Open **Phase instructions** in each chapter. Record the result at that chapter before depending on it elsewhere. Carry Grilling answers into Plan tasks, attach the Build output to the task, record the Testing result, and link Maintenance changes back to the decisions and evidence they affect.
4. Use the exit check below to move the release forward. If a new finding changes an earlier decision, reopen that decision and repeat the affected work. Keep the current phase and the next action visible in the Bible.

For example, in Zoo Helper, the visitor queue starts with a decision about what a child should see and hear. Plan turns it into a task with starting conditions and expected results. Build makes the queue playable and resettable. Testing watches a child try it and checks the cue with sound off. Maintenance links any later fix to the observation that prompted it.

## Phase 1 · Grilling

Work through the applicable chapters with the creator. Use Grill with Docs to make decisions about what you’re trying to make and what people should experience. Save each answer where it belongs in the Bible. Move to Plan when you have enough decisions to describe the release and identify what still needs an answer.

## Phase 2 · Plan

Use Ask Edwards’s gestalt lens as a project planning exercise. Step back from the chapter views and walk through the whole idea as someone would experience it, from opening it to getting what they came for. Look at how the chapter decisions work together. For example, if a player is supposed to learn which ground is safe by looking at it, the art, movement rules, and feedback need to teach the same thing. Resolve gaps and conflicts that would change the build.

Once the release makes sense as a whole, go back through every applicable chapter and outline all the build tasks you can identify from its decisions. Add them to the existing task list under the chapter they belong to. Say what each task should produce, what it depends on, and how you’ll know it works. Put unanswered decisions beside the tasks they block. Move to Build when the team has a usable task list and can see what to do first.

## Phase 3 · Build

Build the full scope agreed in Plan. Use the sandbox and the minimum checks needed to keep building with confidence: confirm a piece works and that the next piece can use it. Assemble the pieces into a complete candidate. Move to Testing when someone can open or install it the way the intended audience will and exercise the whole release.

## Phase 4 · Testing

Put the integrated candidate through the major checks. Walk the real user journeys end to end on the intended devices, playtest or try the workflows with people where appropriate, and check the failure and recovery paths. Fix what breaks and repeat the affected checks. When this phase is complete, the product is ready to show and ship.

## Phase 5 · Maintenance

Once the product is shipped or handed over, collect feedback and make the edits people ask for. Record fixes, updates, and what you verified. If a bigger change needs its own release, work through the same phases for that release.
